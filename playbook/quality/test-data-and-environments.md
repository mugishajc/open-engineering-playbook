# Test data and environments

The problem: "Tests fail because someone changed the shared test customer, and the only realistic data we have is a copy of production with real names in it." Use synthetic data by default, generated by code that lives with the tests and changes with the schema. Allow data derived from production only through an approved, automated masking pipeline with a deletion date. Create test environments on demand from code, isolate each test run, and keep differences from production on a written list. The base rules are in [environments](../delivery/environments.md#production-data-rules) and [testing](../delivery/testing.md#test-data-and-privacy); this page adds the techniques.

## Outcomes

Starting points. Tune them to your data and platform.

| Signal | Starting target |
|---|---|
| Copies of production personal data outside production without an approved record | Zero, as in [environments](../delivery/environments.md) |
| Automated tests that create their own data and do not depend on data another test changes | 100% |
| Approved masked copies deleted on their recorded date | 100%, at most 30 days after creation |
| Schema changes that update the synthetic data generators in the same pull request | 100% |
| Time to create a test environment with seeded data | Under 15 minutes, as for preview environments |
| Test failures caused by environment or data problems rather than the product or the test | Tracked weekly; under 5% of failures on `main` |

## Choose the data source

| Source | Use for | Rules |
|---|---|---|
| Factories and builders in test code | Unit, component and integration tests: the default | Each test builds only what it needs; random values from a fixed, logged seed |
| Seeded synthetic data sets | Preview environments, end-to-end tests, demos, training, UAT | Generated from code, versioned, realistic shape |
| Synthetic data at volume | Performance and volume tests | Realistic distributions and skew at production size; see [performance testing](performance-testing.md) |
| Masked production-derived data | Reproducing a performance problem, rehearsing a migration, rare real-world cases that are hard to generate | Approved masking pipeline, approval record, deletion date |
| Production itself | Synthetic probes, testing in production, audited debugging | Test accounts flagged and excluded from business reports; time-limited, audited access |

## Synthetic data done well

- **Realistic shape.** Match production distributions: a few very large customers and many small ones, long and short names, scripts other than Latin, several currencies and time zones, records that are years old. Uniform random data hides the problems real data causes.
- **Referential integrity.** Generated records link correctly across tables and services.
- **Deliberate edge cases.** Add the cases incidents taught you: the customer with 10,000 orders, the name with an apostrophe, the account opened on 29 February.
- **Deterministic.** Generation from a fixed seed gives the same data set every time, so failures can be reproduced.
- **Obviously fake.** Use reserved names and ranges that cannot reach a real person: the `example.com`, `.example` and `.test` domains reserved by RFC 2606, telephone ranges your regulator reserves for fiction or testing, payment card numbers from your payment provider's test set, national identity numbers that fail their checksum.
- **Owned and versioned.** Generators live in the repository, have code owners, and change in the same pull request as the schema.

Synthetic data produced by a model trained on real records can reproduce some of them, especially unusual ones. Treat it as personal data until a privacy assessment shows it is not.

## Masking and anonymisation

Under EU and UK GDPR, pseudonymised data (where the link to a person can be restored with extra information) is still personal data (Article 4(5) and Recital 26). Data is anonymous only when no one can reasonably identify a person from it, taking into account all the means likely to be used. Most "masked" test copies are pseudonymised, not anonymous, so data protection law still applies.

| Technique | What it does | Watch for |
|---|---|---|
| Substitution | Replaces names, addresses and identifiers with generated values | Keep the same substitute for the same value across tables (deterministic mapping with a secret key held only in production) |
| Shuffling | Moves real values between records | Rare values still identify people |
| Format-preserving tokenisation | Keeps format and validation rules (length, checksum) | The token vault stays in production |
| Generalisation | Age band instead of date of birth, district instead of address | Too coarse for some tests |
| Suppression | Removes a field | Tests that need the field |
| Noise | Adds small random changes to numbers and dates | Totals and reconciliations no longer match |

Rules for the masking pipeline:

1. **It runs inside the production boundary.** Only the masked output leaves.
2. **It fails closed.** A column or field not listed in the masking rules is dropped, so a new column added by a migration cannot leak.
3. **Free text and files are dropped or replaced.** Notes, comments, attachments and images are where personal data hides.
4. **Indirect identifiers are checked.** Combinations such as postcode, date of birth and sex can identify a person. As a starting point, no combination of these fields is shared by fewer than 5 records in the output.
5. **Rules are versioned and reviewed** by the data owner and the data protection officer (or delegate), and each copy has an approval record with purpose and deletion date, as in [environments](../delivery/environments.md#production-data-rules).

Know the limits of masking before you rely on it:

- **Groups of 5 do not stop attribute disclosure.** If all 5 records that share a postcode, birth year and sex have the same diagnosis, the diagnosis is disclosed. Check sensitive fields within each group, not only group size.
- **Exact values link to other data.** Exact amounts, timestamps and locations can be matched with data the tester can see elsewhere: a payment of 4,317.50 at 09:12 identifies one person. Round, band or shift them where the test allows.
- **Rare records stay rare.** The one customer with 10,000 orders, or the only account in a small town, is recognisable after any substitution. Drop or generate those records.
- **The mapping key is the data.** Whoever holds the substitution key or token vault can reverse the masking. Keep it in production and never in the test environment.

Because of these limits, prefer synthetic data, and treat every masked copy as personal data with the controls above.

ISO/IEC 20889:2018 describes de-identification techniques and their properties, and NIST SP 800-188 gives guidance for government data sets.

## Environments for testing

[Environments](../delivery/environments.md) sets the shape: few long-lived environments, previews per pull request with a 72-hour time to live, the same artifact everywhere, a written parity list. For testing, add:

- **Isolation per run.** Integration tests start their own database, queue and cache in containers (for example with Testcontainers). No test run shares state with another.
- **Fakes for third parties**, through service virtualisation (for example WireMock) or the provider's sandbox, kept honest with contract tests. Record on the parity list how each sandbox differs from the real service: rate limits, missing features, different error responses.
- **A health check before tests run.** A short smoke test confirms the environment and its dependencies are up. If it fails, the run is reported as an environment failure, not a test failure.
- **Classify every failure** as product defect, test defect, environment or data. Teams cannot fix what they cannot see, and environment failures erode trust in tests fastest.
- **Control time.** Inject a clock, or use a tool that fakes system time in a dedicated environment, to test month-end, year-end, leap days and daylight saving changes without waiting for them.
- **A performance environment** sized like production, booked on a schedule, with production-sized synthetic data. Shared by teams, owned by one.
- **UAT runs in staging** with integrations in sandbox mode and realistic data, not in an extra long-lived environment.

## Practice

### Foundation

- Factories and builders in tests; no shared, mutable test records.
- A seed script that loads a small, realistic synthetic data set into local and preview environments.
- No production personal data outside production. Debug production problems in production, with audited access.

### Standard

- Synthetic data generators versioned with the schema and code owned.
- Preview environments seeded automatically; integration tests isolated in containers.
- Failure classification and an environment health check on every pipeline run.
- Masked copies only through the fail-closed pipeline, with approvals and deletion dates.
- DORA's test data management capability as the check: tests have the data they need, do not compete for it, and teams can create it themselves.

### Assured

- A data protection impact assessment for any use of production-derived data in testing (see the [DPIA template](../../templates/security/dpia.md)).
- Test data controls mapped to ISO/IEC 27001:2022 Annex A 8.33 (test information), with records of each copy, its approval and its deletion.
- Masking rules and anonymisation checks reviewed yearly by the data protection officer, and re-run when the schema changes.
- Data residency rules apply to every environment that holds production-derived data, including backups and logs.

## Cloud, on-premises and air-gapped

- **Cloud:** keep non-production in separate accounts or projects. A masked copy must stay in the regions that residency rules allow.
- **On-premises:** masking runs on production infrastructure; plan the compute and storage it needs.
- **Air-gapped:** data from a classified network cannot leave it, so testing that needs realistic data happens inside. Synthetic data generators, container images and fake services come in through the mirror and the import process.

## Anti-patterns

| Anti-pattern | Fix |
|---|---|
| Nightly copy of production into staging | Synthetic data; masked copies only by exception, with approval and deletion date. |
| A masking script that lists the columns to mask | Fail closed: list the columns allowed through, drop the rest. |
| Notes and attachments copied "because they are not personal data" | Drop or replace all free text and files. |
| Shared test accounts that tests change | Each test creates its own data. |
| Uniform random synthetic data | Production-shaped distributions and deliberate edge cases. |
| Environment failures reported as test failures | Health check first; classify every failure. |
| Waiting for month-end to test month-end | Inject or fake the clock. |
