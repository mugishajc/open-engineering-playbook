# Code review

Every change to production code gets reviewed by at least one person other than the author before it merges. Review exists to catch defects, keep the design healthy and spread knowledge across the team. It is not a gate for seniority or taste, and it fails when it is slow: reply to a review request within one working day.

## Outcomes

Starting targets. Tune them after one quarter of data.

| Signal | Starting target |
|---|---|
| Time to first review response (working hours) | Median under 4 hours, 90th percentile under 1 working day |
| Pull requests under 400 changed lines (excluding generated files and lockfiles) | At least 80% |
| Pull requests merged without any approving review | Zero, outside logged break-glass |
| Review rounds before merge | Median 2 or fewer |
| Escaped defects where review was the obvious place to catch them | Tracked in postmortems and trending down |
| Engineers who reviewed at least one change outside their usual area this quarter | At least half the team |

## Why we review

In priority order:

1. **Correctness.** The change does what it claims and does not break something else.
2. **Design.** The change fits the system and will be easy to change next year.
3. **Knowledge sharing.** At least two people understand every part of the code.
4. **Consistency.** The code follows team conventions so the next reader moves fast.

Review is not the place to enforce formatting (use a formatter), catch what a linter catches (use a linter), or reargue a design that an [RFC](../architecture/rfcs.md) or [decision record](../architecture/decision-records.md) already settled.

The standard to approve is Google's: approve when the change definitely improves the overall health of the code, even if it is not perfect. Perfection is not the bar. Continuous improvement is.

## Practice

### Foundation

#### Author responsibilities

- **Keep it small.** Aim for under about 400 changed lines. Split refactoring from behaviour change. Split one feature into a series of small, safe pull requests behind a [feature flag](feature-flags.md).
- **Self-review first.** Read your own diff in the review tool before you ask anyone. Remove debug output, commented-out code and unrelated changes.
- **Write the description.** Use the [pull request template](../../templates/github/PULL_REQUEST_TEMPLATE.md): what and why, how you tested it, risk and rollback, checklist. Link the issue. Add screenshots for UI changes.
- **Make CI green before asking.** Reviewers should not spend time on a change that does not build.
- **Pick the right reviewers.** CODEOWNERS adds the owning team. Add a specialist for security, data or infrastructure changes.
- **Respond to every comment.** Fix it, or reply with why not. Resolve threads only when the reviewer agrees or the point is a non-blocking label.
- **Own the result.** You own every line you submit, including code generated by tools or code assistants. See [Code produced with code assistants](#code-produced-with-code-assistants).

#### Reviewer responsibilities

- **Respond within one working day.** A first response can be a full review, a question, or "I cannot review this until Thursday, please ask someone else". Silence is the only wrong answer.
- **Review the whole change.** Read the description and the tests first, then the code.
- **Label every comment** so the author knows what blocks merge (see below).
- **Approve when it is good enough.** Approve with non-blocking comments rather than holding a change for nits.
- **Be kind and specific.** Comment on the code, not the person. Explain why. Offer a concrete alternative.

Solo engineers: review your own pull request the next morning, with fresh eyes, against the checklist below. Use a second reviewer for anything touching authentication, payments, personal data or production infrastructure, even if that means asking a contractor or a peer outside the company.

### Standard

#### What to look for, in priority order

| Priority | Question | Examples |
|---|---|---|
| 1 | Is it correct? | Logic errors, edge cases, off-by-one, null handling, concurrency, time zones, money rounding |
| 2 | Is it safe? | Input validation, authorisation checks, injection, secrets, personal data in logs |
| 3 | Is it tested? | Tests fail without the change, cover the edge cases, do not depend on time or order |
| 4 | Can it fail safely? | Error handling, timeouts, retries with limits, rollback plan, migration compatibility |
| 5 | Is the design right? | Right layer, right module, no new coupling, matches decision records |
| 6 | Can we run it? | Logs, metrics, traces, alerts, runbook updates. See [observability](../architecture/observability.md) |
| 7 | Can the next person read it? | Names, comments that explain why, no dead code |
| 8 | Is it consistent? | Team conventions not covered by tools |

Stop and send the review back if the change is too large to review well. Ask the author to split it.

#### Comment labels

Start each comment with a label. These are based on Conventional Comments.

| Label | Meaning | Blocks merge? |
|---|---|---|
| `blocking:` | Must change before merge. Explain the risk. | Yes |
| `question:` | I do not understand. Answer it, and add a code comment if the answer is not obvious from the code. | Until answered |
| `suggestion:` | A better way, in my view. Author decides. | No |
| `nit:` | Minor style or naming point. Author decides. | No |
| `praise:` | Something done well. Use it. | No |
| `follow-up:` | Worth doing, not in this change. Author opens an issue. | No |

If more than a third of your comments are `nit:`, automate the rule in a linter or formatter instead.

#### Turnaround

- First response within **one working day** of the request. The playbook starting target for the median is 4 working hours.
- Re-review within **4 working hours** of the author pushing changes.
- Authors who need speed ask in the team channel. Reviewers protect focus time by reviewing in two or three fixed slots per day rather than on every notification.
- Teams across time zones assign a reviewer in an overlapping zone for urgent changes.

#### Disagreement and escalation

1. Discuss on the pull request. Each side states the risk in concrete terms.
2. If two rounds of comments do not settle it, talk for 15 minutes on a call. Write the outcome on the pull request.
3. If still stuck, the code owner for that path decides. If the code owner is a party, the tech lead decides.
4. If the disagreement is about design direction, not this change, merge the change if it is safe and open an [RFC](../architecture/rfcs.md) or [decision record](../architecture/decision-records.md).

Escalation should take less than 2 working days end to end. A reviewer who blocks must give the author a path to approval.

#### Changes that need more care

| Change type | Extra rules |
|---|---|
| Tests | Check that the test fails without the change. Watch for tests that assert nothing, sleep, or depend on network or wall-clock time. See [testing](testing.md). |
| Database migrations | Check backward compatibility with the running version, locking behaviour on large tables, and the rollback path. Require a code owner from the data team. See [database changes](database-changes.md). |
| Security-sensitive code (auth, crypto, payments, personal data, input parsing) | Security champion or security team review. Check against the threat model. See [secure development](../security/secure-development.md). |
| Infrastructure as code and CI | Read the plan output, not only the diff. Check IAM scope, network exposure, secret handling and pinned versions. See [continuous integration](continuous-integration.md). |
| Dependency updates | Read the changelog for major versions. Check licence and maintainer changes. See [dependencies](../security/dependencies.md). |
| Public API changes | Check versioning and deprecation. See [API standards](../architecture/api-standards.md) and [versioning](versioning-and-changelogs.md). |

#### CODEOWNERS

- Map paths to teams, never to individuals who might leave.
- Require code owner review on risky paths (migrations, auth, CI workflows, infrastructure, CODEOWNERS itself).
- Keep the owning team for each path to at least 3 people so review never waits for one person on leave.
- Templates: [GitHub](../../templates/github/CODEOWNERS), [GitLab](../../templates/gitlab/CODEOWNERS).

### Assured

Review becomes a control with evidence: separation of duties.

- **Two-person rule.** The author cannot approve their own change. At least one approver who is not the author must approve the final version. On GitHub, enable `require_last_push_approval` so the last person to push cannot be the approver. On GitLab, prevent approval by the author and by committers.
- **Stale approvals are dismissed.** A new push after approval resets approval.
- **Two approvers** for changes to authentication, authorisation, cryptography, payment flows, production access, CI pipelines and the review rules themselves.
- **Break-glass.** An emergency change can merge with one approval or none, through a named group of 2 to 3 people. Each use creates a ticket, and a second person reviews the merged change within 1 working day.
- **Evidence.** The platform keeps the pull request, approvals, CI results and linked ticket. Retain them for your records retention period. Export them for auditors rather than taking screenshots.
- **Map to controls.** This gives evidence for ISO/IEC 27001:2022 Annex A 8.25, 8.28 and 8.32, SOC 2 CC8.1, and NIST SSDF practice PW.7 (review code for vulnerabilities). See [control mapping](../compliance/control-mapping.md).

## Code produced with code assistants

Code assistants change who types the code. They do not change who owns it.

- The author owns every line, as if they had written it by hand. "The assistant wrote it" is never an answer to a review comment.
- The author must be able to explain any line a reviewer asks about.
- Reviewers apply the same bar. Do not relax review because a change looks tidy; generated code can be fluent and wrong.
- Watch for invented APIs and packages, outdated library usage, missing error handling, tests that mirror the implementation instead of the requirement, and licence-encumbered snippets.
- Large generated changes follow the same size rule. Split them.
- Follow your organisation's [code assistant page](../people/code-assistants.md) and [policy template](../../templates/docs/code-assistant-policy.md) on what data may be shared with which tools.

## Metrics

Watch these at team level to improve the process:

- Time to first review and time to merge (median and 90th percentile).
- Pull request size distribution.
- Number of review rounds.
- Review depth: share of pull requests that get at least one substantive comment or question. A very low share on large changes suggests rubber-stamping.
- Spread of reviewers: how many people review each area.

**Do not use review metrics to rate individual performance.** Count of comments, count of approvals, pull requests merged per person and lines of code all reward the wrong behaviour. People split work artificially, approve without reading, or leave noise comments. Use the metrics to fix the process, and see [metrics](../measurement/metrics.md).

## Cloud, on-premises and air-gapped

Every practice here works on self-hosted GitLab, GitHub Enterprise Server, Gitea or Forgejo and Bitbucket Data Center. Check which approval rules your edition supports (code owner approval and last-push approval vary by edition and version). In air-gapped networks, reviewers cannot open external links, so authors paste the relevant part of any external document into the description.

## Anti-patterns

| Anti-pattern | Fix |
|---|---|
| 2,000-line pull requests approved with "LGTM" | Enforce the size target. Reviewers send large changes back. |
| Review queues of several days | Track time to first review. Fixed review slots. Spread ownership. |
| Comments without labels, author cannot tell what blocks | Use the label table. |
| Style debates in review | Automate formatting and linting in CI and pre-commit. |
| One senior engineer must approve everything | CODEOWNERS with teams of 3 or more. Grow reviewers by pairing. |
| Approvals counted in performance reviews | Remove it. Measure team flow, not individual counts. |
| Self-approval through a second account or admin merge | Last-push approval, no standing bypass, audit log review. |
